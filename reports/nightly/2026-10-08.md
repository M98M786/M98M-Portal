### 3. The out-of-stock bell rang hourly instead of daily — HIGH — FIXED, DEPLOY PENDING

`stockWatch` rides the hourly cron and its ref is day-stamped, so every listing still at zero stock
re-rang **every hour**: 22 copies of the identical `(recipient, ref)` bell per item on 7 Oct, 6,814
bells in the day against 2,860 real events. That is why the trays are unreadable — Husnain carries
**31,332** unread and Zain **29,788**.

Root cause is an asymmetry inside `queueNotify`. Its *letter* half guards itself —
`WHERE NOT EXISTS (… to_addr = ?1 AND ref = ?4)`, commented "Same (recipient, ref) never files
twice" — which is why `alert_log` holds ~126 of these and not thousands. Its *bell* half goes
through `notifInsert`, whose `INSERT OR IGNORE` is keyed on `as_id`, and every engine-raised bell
passes `as_id ''`. The letter filed once while the bell rang all day.

Fix (`fdcd623`): `stockWatch` now asks `alert_log` what has already gone out today and skips those
items. Deliberately per **item**, not per job-run — `darkAccountWatch`'s whole-job cursor would have
been wrong here, because a listing that empties at 14:00 must still ring within the hour. Expected
effect: ~6,814 bells/day → ~2,860.

**Not live.** The dash multipart PUT was refused by the `javascript_tool` permission classifier —
the same refusal recorded on 24 Sept, which memory says not to loop on. There is no second channel
(no `cf_token`, no wrangler). The Cloudflare dash session itself is healthy, so this is purely the
local classifier. `engine-worker.txt` therefore sits **ahead** of the deployed worker at
1,455,497 units — that drift is a pending deploy, not a stale mirror. **First job for the next run.**

### 4. The hunter's calculator showed raw server errors mid-typing — MEDIUM — FIXED AND LIVE

`calcProjectedProfit` was the single noisiest error in the Apps Script log: 22 × `soldFor must be a
number` plus 2 × `sourcePrice must be a number` in 30 h.

The live projection fires on a 450 ms debounce as the hunter types. Its idle guard used
`huFirstNumber`, which digs the *first* number out of anything — `"12.50 + £4"` reads as 12.5 and
passes — while the server parses the *whole* string (`brainParseAmount_`: strip `£ $ ,` and spaces,
then a strict `lo-hi` range or `Number()` on all that is left). Every value the two disagreed about
fired a doomed call on each debounce tick and put the server's own wording in front of the hunter.

Fix (`3a1e954`, build `20261007-2204`): the guard mirrors the server's rule, so a half-typed cell
just leaves the calculator on its hint; a filled-in Source Price that cannot be read gets its own
line naming that cell. Values are still sent **raw**, so ranges behave exactly as before.

Verified live on Pages (`huServerAmount` present in the served bundle, 8 polls) and parity-tested
against the real server parser — 5 previously-doomed inputs now stay idle (`12.50 + £4`,
`12.50 (approx)`, `12.5+4`, `0`, `-5`), ranges and plain prices unchanged, **0 regressions**.
